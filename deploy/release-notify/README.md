# Сообщение о выпуске библиотеки в чатах 101

`design-release-notify.timer` каждые 10 минут запускает серверную проверку. Когда в npm появляется новая версия `@101app/design-tokens-web`, каждый адресат получает одно сообщение в личный чат 101 AI:

```text
Библиотека дизайна 101 обновлена
Версия: 1.0.203
Web: npm install @101app/design-tokens-web@1.0.203
iOS и Android: тег 1.0.203

Что изменилось
• Добавлена иконка phone-incoming
• Добавлена иконка phone-outgoing
Полный список изменений
```

Подписи и заголовок «Что изменилось» в чате выделены жирным. В сводке перечислены добавленные, обновлённые, удалённые и переименованные иконки, изменения цветов, стилей и других токенов. Короткий список содержит до 12 пунктов и ссылку на полное сравнение коммитов. Произвольный текст и адресаты через аргументы не принимаются.

Служба не входит в workflow `Release Design Tokens` и ничего не получает от него. Она смотрит на опубликованный результат, поэтому сбой отправки или недоступность 101 не влияют на выпуск, а исполнитель сборки по-прежнему не имеет доступа к реквизитам отправителя.

## Что считается выпуском

Сообщение ставится в очередь, только когда выполнены все условия:

1. `https://registry.npmjs.org/@101app%2Fdesign-tokens-web/latest` отдаёт числовую версию `X.Y.Z` и `designTokensSourceCommit`.
2. Версия больше `announce_after_version` из настроек и больше любой уже записанной версии.
3. В `101-APP/design` есть Git-тег с тем же номером, и он указывает на тот же коммит, что и `designTokensSourceCommit`.
4. GitHub отдаёт сравнение с последней записанной версией или с `announce_after_version` при первом запуске. Если два номера указывают на один коммит, сообщение сообщает, что ресурсы не изменились. Если начального тега нет, сообщение содержит ссылку на исходники выпуска.

Пока тег выпуска отсутствует, коммиты расходятся или сравнение временно недоступно, сообщение не создаётся; результат прохода содержит `unverified` и код причины. Проверка повторится на следующем проходе. Если GitHub достиг лимита ответа для большого сравнения, сообщение содержит ссылку на полное сравнение.

Ограничения:

- Проверяется только последняя версия npm. Если между проходами вышли две версии, сообщение будет об одной, последней. Недоставленное сообщение о прежней версии получает состояние `superseded` и позже не отправляется.
- Git-тег подтверждает исходник для iOS и Android, но не готовность Android-пакета: JitPack собирает его при первом запросе версии.
- GitHub опрашивается без ключа и только при появлении необъявленной версии. Обычный проход — один запрос к npm, без входа в 101. Ответ со сравнением или содержимым токенов ограничен 2 МиБ.

## Отправка и квитанции

Контракт совпадает с `frontend-notify`: `POST https://app.101-group.ru/api/user/login/`, затем `POST /api/assistant-messages/` с `Authorization: JWT`. Вход обязан подтвердить закреплённого отправителя; ключ входа остаётся в памяти и передаётся только на адрес отправки сообщений. Перенаправления не выполняются, TLS проверяется, ответ ограничен 64 КиБ, запрос — 10 секундами.

Текст и `clientMessageId` сохраняются в `/var/lib/design-release-notify/state.json` до входа и отправки. Ключ — SHA-256 от `design-release:v1:<версия>:<адресат>`, поэтому повтор после потери ответа возвращает прежнее сообщение. У каждого адресата своя запись:

- `sent` — 101 принял сообщение; ответ 201 сверен по адресату, тексту и номерам сообщения и чата. Это не подтверждение прочтения.
- `pending` — отправка повторится. Сетевая ошибка, 401, 429, 5xx и отказ входа повторяются с растущей задержкой до 30 минут.
- `blocked` — 400, 403, 404, 409 или перенаправление. Автоматически не повторяется.
- `superseded` — вышла более новая версия раньше, чем сообщение было доставлено.

Хранятся записи о 20 последних версиях. Чаты адресатов служба не читает.

## Настройки

`/etc/design-release-notify/config.json`, `root:root`, режим `0600`, формат — в `config.example.json`:

- `sender_guid` — идентификатор отправителя; должен совпадать с `sender_guid` реквизитов и с ответом входа.
- `recipients` — от одного до десяти идентификаторов людей, без повторов. Указывать точно так, как они записаны в 101.
- `announce_after_version` — граница: объявляются только версии строго больше. При установке указать текущую опубликованную версию, иначе она будет объявлена как новая.

Имена и идентификаторы людей в репозиторий не добавлять: он публичный. Новый адресат получает сообщения начиная со следующего выпуска; удалённому адресату не отправляются и ранее отложенные сообщения.

Реквизиты отправителя не копируются. Служба получает через `LoadCredential` уже существующий `/etc/101-frontend/notification-source.json` (`format_version`, `base_url`, `email`, `password`, `sender_guid`). Пароль и ключ входа не попадают в аргументы, состояние и журнал; в журнал выводятся только безопасные коды.

## Установка

Выполняет администратор сервера из проверенного состава репозитория. Перед установкой убедиться, что на сервере есть `/usr/bin/python3` и файл реквизитов по указанному пути; если отправитель хранится в другом месте, поправить `LoadCredential` в файле службы.

```sh
install -d -o root -g root -m 755 /usr/local/libexec/design-release-notify
install -o root -g root -m 755 notify.py /usr/local/libexec/design-release-notify/notify.py
install -d -o root -g root -m 700 /etc/design-release-notify
install -o root -g root -m 600 config.json /etc/design-release-notify/config.json
install -o root -g root -m 644 systemd/design-release-notify.service systemd/design-release-notify.timer /etc/systemd/system/
systemd-analyze verify /etc/systemd/system/design-release-notify.service /etc/systemd/system/design-release-notify.timer
systemctl daemon-reload
```

Проверки до включения расписания, обе без отправки сообщений:

```sh
/usr/bin/python3 -I -B /usr/local/libexec/design-release-notify/notify.py --dry-run
systemd-run --wait --collect --unit=design-release-notify-auth \
  -p LoadCredential=notification-source.json:/etc/101-frontend/notification-source.json \
  /usr/bin/python3 -I -B /usr/local/libexec/design-release-notify/notify.py --check-auth
```

`--dry-run` читает настройки, npm и GitHub; при верной границе отвечает `"release": "not_new"`. `--check-auth` только подтверждает вход отправителя; результат — в `journalctl -u design-release-notify-auth`. Затем:

```sh
systemctl enable --now design-release-notify.timer
systemctl list-timers design-release-notify.timer
```

Настоящая доставка проверяется на следующем выпуске библиотеки: в `journalctl -u design-release-notify.service` появится строка с `"release": "queued"` и числом `sent`, равным числу адресатов. Понижать `announce_after_version` ради проверки можно только осознанно: все адресаты получат настоящее сообщение о текущей версии.

## Восстановление

- Результат каждого прохода — одна строка JSON в журнале службы. `pending` и `blocked` показывают число недоставленных записей.
- `blocked` разбирается вручную по `last_error` в `state.json`. После устранения причины администратор при остановленном таймере возвращает конкретной записи `"state": "pending"`, не меняя её ключ и текст. Удалять записи или менять ключ ради повторной отправки нельзя: это создаст дубль.
- Повреждённый `state.json` останавливает проход с кодом `STORE_INVALID`; служба его не перезаписывает.
- Одновременный второй запуск завершается с `ALREADY_RUNNING`.

## Тесты

```sh
python3 -I -B deploy/release-notify/tests/test_notify.py
```

Тесты подменяют npm, GitHub и 101 и проверяют очередь, повторы с прежним ключом, блокировку отказов, границу версий, сверку тега, закрытость файлов и то, что ключ отправителя не уходит на чужие адреса. Описания служб systemd и настоящая доставка проверяются отдельно на сервере.
